审计日期：2026-09-29。代码基线：`aeac30a136f753c8aff0bfc41dc496624e630b87`。
本文件为执行顺序与阶段验收的唯一当前计划；

## 总目标与完成定义

交付一个使用 Node.js 26／TypeScript、必要时使用 Rust 数学库的完整产品：
在无 Python 环境完成构建、安装、启动、打印、维护、升级与恢复；完整替代
约定上游的 Moonraker；以受控产品操作替代任意宏；运动精度和打印性能经
目标板及实机验证。现有 C MCU 固件与 C 运动内核可保留。库与语言选择服从
数值正确性、批量调用开销和目标设备结果，不以重写数量为目标。

完成须同时成立：默认入口和所有维护／测试入口不依赖 Python；原有功能
均有替代及验收映射；Moonraker 全量契约闭合；宏使用场景完成产品替代；
已知数值与崩溃问题关闭；目标设备达标；规定的集成和发布流程完成。
第一台机器通过只是一项里程碑，不缩减其他机型、设备或完整功能范围。

## 审计结论

1. 9 月 26 日计划已有正确的大方向，执行缺少阶段出口与任务准入。
   在运动数值异常和实机入口尚未关闭时，连续扩展外围传感器，未优先
   消除整体交付阻碍。不能再用“又完成一个模块”推定接近完成。
2. 文档治理失效：迁移记录已有 28,039 行，最新进展、早期状态矩阵与
   历史执行顺序混杂。历史表格不能作为当前待办或完成率分母。
3. 已有实质性资产：独立编译包、生产依赖安装、服务生成、原生运动和
   打印状态机、文件管理、模拟 MCU 的编译 HTTP 打印流程。应复用这些
   资产建立真实交付包，不再重新从算法或协议层开始规划。
4. 产品装配仍依赖外部 `createAdapter`，要求停止回调、生命周期、文件
   准入和服务鉴权。验收代码使用测试密钥与模拟 MCU，不能证明真实板卡

5. Python 残留有两个维度：177 个跟踪文件均在 klippy；安装与 CI 仍有
   Python 依赖。另有 49 个 host 文件匹配直接调用 python3 的三类模式
   （execFileSync／spawnSync／spawn），这是有限静态搜索，不是完整调用图。
   冻结参考数据可消除日常回归依赖；不能只删 .py 文件宣布退役。
6. Moonraker 已固定上游提交，但现有清单明确只是注册点目录，含动态
   表达式，状态也是早期快照。必须展开契约并映射当前实现；目录中有文件
   或 HTTP 返回成功均不能证明组件完整。
7. 精度异常与崩溃仍未定因。已有逐核心、运行时和 C 对照证据不能被
   后续成功运行覆盖。扩大随机重跑不是关闭问题的计划。

## 从整体到任务的分解

每个任务必须属于一条完整交付链，并说明它解除了哪一个阶段出口的缺口。

| 整体交付链 | 向下分解的职责 | 最终可观察结果 |
| --- | --- | --- |
| 安装到就绪 | 产物、依赖、机器配置、板卡适配、鉴权、服务生命周期 | 干净目标环境安装后启动，无 Python 与测试替身 |
| 文件到实体打印 | 文件准入、准备、归零／调平、加热、规划、步进、完成收尾 | 同一发布产物完成真实打印，输出质量和速度达标 |
| 异常到可恢复状态 | 急停、超时、断连、进程退出、断电、日志、人工确认与重新归零 | 输出停止，状态诚实，不自动重放危险动作 |
| 客户端到完整服务 | 传输、用户／授权、文件、作业／队列／历史、数据库、机器与外部集成 | 固定 Moonraker 契约和真实客户端流程通过 |
| 用户意图到受控动作 | 开始／暂停／恢复／取消、换料、校准、维护、旧宏迁移 | 用户无需编写脚本，参数、权限、互斥、幂等与恢复明确 |
| 源码到可维护发布 | 构建、烧录、诊断、测试、升级、回滚、依赖与文档 | 无 Python 的可重复交付及后续维护 |

模块是这些链路的依赖，不能成为脱离链路的独立进度目标。

## 下一步可直接执行的工作

1. **完成 G0 台账**。从 Git 文件、启动脚本、包依赖、测试子进程、动态
   配置加载和现有契约中建立可追踪清单。177 个 Python 文件逐项关联
   替代入口或明确缺口；复核所有 Python 调用，分类为默认运行、工具、
   日常测试或一次性参考捕获。记录分类依据，不用同名 TS 文件自动认定迁移。
2. **确定 G1 的真实装配差距**。先检查仓库已有机器配置与硬件约束，选出
   可验证的候选基线；型号、配置和访问方式不明确时才向用户索取必要信息。
   将机器 JSON／板卡适配／用户鉴权／停止输出逐项追到真实实现，形成
   “已接通、测试替身、未接通”表，然后修复首个影响安装到打印的缺口。
   缺硬件时继续完成本机实现与可交付产物，不把模拟成功写成物理成功。
3. **G2 独立专项**。整理每个历史失败的输入、二进制、原生扩展、线程及
   环境，区分离线诊断异常与生产运动路径，验证共用依赖和影响范围。
   每轮实验先写假设、辨别结果与下一步；无新增辨别能力时停止重复试跑，
   转向不同环境、实现或工具。确认需要独立环境后请求明确资源。
4. **数值实现决策**。对确认为关键的失败路径，比较修复后的 TS／专用库、
   现有 C 内核以及必要的 Rust 批量计算路径。用相同输入比较误差、
   边界、序列化／跨语言开销、吞吐及尾延迟。Rust 不自动解决硬件或运行时
   故障；采用与否必须有证据，也不能仅凭诊断异常宣布所有运动计算失效。

G0 完成即将第 1、2 项中已确定的首个缺口转成实现任务；不能无限扩张
审计文档而推迟交付。下一轮不默认继续 BME680／BMP388，除非台账证明
它直接阻碍选定机器或当前验收出口；两者仍属于全量范围。

## 实现与验证的任务准入

每项任务的最小记录：需求来源 → 用户路径 → 当前缺口 → 实现改动 →
验证依据／阈值 → 依赖 → 通过后的入口切换或退役动作。
没有对应阶段缺口的便利功能、绘图细节和额外防护不抢占主线。
当前保持一个主要实现任务；测试等待期间可做独立只读核查，不混入新改动。

验证分三级：算法／模块契约、发布产物完整链路、目标硬件验收。改动先跑
最小有意义的受影响检查；每个可交付组合跑完整链路，实机门槛必须在目标
环境完成。已有检查覆盖相同提交且无新风险时不重复。失败保留原始证据；
修复后的成功不能自动关闭未定因失败。

性能先给出预算再测量：规划／步进、时钟、发送队列及高频 API 重点看
吞吐、P95／P99、队列饥饿、命令提前量、CPU／内存、长时间稳定性及实际
打印耗时。阈值须对应目标板、运动上限和误差预算；当前桌面基准仅作
开发回归依据。传感器的微秒 CPU 开销不能推导整机打印提速。
完整 Moonraker 按固定上游展开方法、参数、错误、事件、权限、动态注册和
可选集成契约；可选组件不能因当前机器不用而被标为“完整替换完成”。
宏场景必须说明替代操作、前置条件、权限、取消边界、持久化幂等与故障
恢复；仅拒绝 gcode_macro 配置不能算宏产品化完成。
