## 总目标与完成定义

交付一个使用 Node.js 26／TypeScript、必要时使用 Rust 数学库的完整产品：
在无 Python 环境完成构建、安装、启动、打印、维护、升级与恢复；完整替代
约定上游的 Moonraker；以受控产品操作替代任意宏；运动精度和打印性能经
目标板及实机验证。现有 C MCU 固件与 C 运动内核可保留。库与语言选择服从
数值正确性、批量调用开销和目标设备结果，不以重写数量为目标。

完成须同时成立：默认入口和所有维护／测试入口不依赖 Python；原有功能
均有替代及验收映射；Moonraker 全量契约闭合；宏使用场景完成产品替代；
已知数值与崩溃问题关闭；目标设备达标；规定的集成和发布流程完成。
当前机型适配范围由用户于 2026-09-29 明确限定为 **ANYRAID 品牌
Cycnumbris 500 系列**。型号已确定，不再另选其他品牌或系列作为首台基线；
系列内具体硬件版本、配置和访问方式按实际资料核验，不推测其一致性。
**Moonraker 完整替代是前期最高优先级的功能主线；全部其他机型适配
放到最后。** 其他机型仍保留在总范围，不能阻塞当前系列交付，也不能
因暂缓适配而被标记为已完成。完整 Python 退役、精度与故障保护要求不变。

## 审计结论

### 当前决策：保留最终范围，以集成产品出口调度

**需要调整近期执行方式，不缩减最终目标。** 当前 goal 保留完整 Moonraker、
全部 Python 替代、消费级受控操作、性能与精度要求；本计划将其分解为
可验收的产品批次。Node.js 26／TypeScript 是主路径，专用数学库及 Rust
根据固定数值参考与目标板基准选择，不新增整层重写作为交付前置。

近期目标：**同一独立编译产物内的 Klipper＋原生 Moonraker，先完成真实
客户端的完整文件、打印与恢复流程，再完成 Cycnumbris 500 目标候选包。**
完整 Moonraker 仍是最高优先级功能主线；可选集成逐项保留在 D4，不阻止
核心接口进入 D2/D3 联调。正式发布仍须满足 G1–G5，其他机型统一在 G6。

### 为什么投入很多而交付进展不明显

1. 历史执行连续扩展外围模块，真实客户端及机器装配问题发现偏晚。
2. 计划中旧“下一项 D1 收口”与后续 D2 进展并存，历史记录混入调度指令。
   本次删除重复审计指令，以本节和“下一步”作为唯一调度依据。
3. 同包 HTTP 模拟验收与源码浏览器探针分离；后者缺完整归零、升温和
   多代重初始化，已经两次暴露夹具缺陷。需要复用已有完整验收设施。
4. 文件选择器工具曾长时间阻塞；这属于验证工具受阻，既不能算产品失败，
   也不能无限重复同一调用占用主线。
5. 无目标配置映射、旧 Python 同条件对照和未关闭的数值故障，使桌面
   功能积累无法直接转化为目标设备交付结论。

### 立即执行的最短路径

1. **收口客户端验收设施**：复用 compiled journey 的 MCU 归零／热控和
   代际重初始化，客户端连接同一编译包；保留真实故障状态，不强制 ready，
   不另写一套完整固件模拟器。当前停止后 ADC 发送缺陷及回归先独立收口。
2. **完成 D2 用户流程**：Fluidd 页面上传 → 元数据 → 开始 → 暂停／恢复 →
   完成；另测取消、断连重连、进程重启和需人工确认的恢复。随后复验固定
   Mainsail 的同一流程。config 根缺失、重启语义等按流程中实际阻碍补齐，
   不开放任意配置文件访问或把原生重初始化草率映射为 firmware_restart。
3. **提前准备 D3**：定位 Cycnumbris 500 配置来源、系列内硬件差异、MCU
   固件、停止输出和安装／回滚资料；缺失则明确登记并索取必要资料。
   无资料不虚构配置，也不让这一阻碍停止独立的 Moonraker 开发。
4. **精度专项作为准入门槛持续推进**：每次诊断须有可区分假设的实验及
   判定条件；保留首个失败证据。无新信息时转独立环境或实现对照，避免
   重复随机测试。关闭前不进入真实运动，不以成功样本覆盖已知失败。
5. **D4 按契约和退役台账闭合**：核心流程贯通后继续全部 Moonraker、
   受控宏场景和剩余 Python；每项标明实际替代入口及证据，不能通过缩减
   兼容声明或删除未迁移功能实现“完成”。其他机型到 G6 再展开。

### 执行与验证约束

同时仅推进一个主要实现缺口；每轮明确所属批次、解除的阻碍、变更、
证据和下一项。装配资料与精度诊断可交替推进，不因此启用多个代理。
修复时先跑受影响类型与契约检查，再跑一次相应同包完整流程；仅新变更、
失败或未覆盖风险触发扩大验证。低频路径检查资源及事件循环影响，高频
路径检查吞吐、尾延迟；每个替代保留必要性能证据。

交付级基准必须比较同设备、输入和配置下的旧 Python 与新路径，并比较
空载及鉴权、上传、订阅、数据库并发负载，记录步进发送提前量、队列饥饿、
P95/P99、内存和打印耗时。运动数学使用固定参考、边界用例和明确误差预算，
不放宽容差；缺少目标板、旧路径对照或误差预算时，门槛仍为待验。

浏览器工具阻塞后先判断工具状态及替代验证路径；API 验证可继续，但页面
验收单列待办，不把接口结果充当 UI 通过。没有目标设备证据前不承诺交付
日期，进度报告以本表出口变化为准，不以新增模块或测试数量为准。

## 实现与验证的任务准入

每项任务的最小记录：需求来源 → 用户路径 → 当前缺口 → 实现改动 →
验证依据／阈值 → 依赖 → 通过后的入口切换或退役动作。
没有对应阶段缺口的便利功能、绘图细节和额外防护不抢占主线。
当前保持一个主要实现任务；测试等待期间可做独立只读核查，不混入新改动。

验证分三级：算法／模块契约、发布产物完整链路、目标硬件验收。改动先跑
最小有意义的受影响检查；每个可交付组合跑完整链路，实机门槛必须在目标
环境完成。已有检查覆盖相同提交且无新风险时不重复。失败保留原始证据；
修复后的成功不能自动关闭未定因失败。

性能先给出预算再测量：规划／步进、时钟、发送队列及高频 API 重点看
吞吐、P95／P99、队列饥饿、命令提前量、CPU／内存、长时间稳定性及实际
打印耗时。阈值须对应目标板、运动上限和误差预算；当前桌面基准仅作
开发回归依据。传感器的微秒 CPU 开销不能推导整机打印提速。
完整 Moonraker 按固定上游展开方法、参数、错误、事件、权限、动态注册和
可选集成契约；可选组件不能因当前机器不用而被标为“完整替换完成”。
宏场景必须说明替代操作、前置条件、权限、取消边界、持久化幂等与故障
恢复；仅拒绝 gcode_macro 配置不能算宏产品化完成。
