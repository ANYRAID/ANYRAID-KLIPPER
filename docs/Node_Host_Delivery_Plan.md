# Klipper 与 Moonraker 集成交付计划

审计日期：2026-09-30；当前源码基线：`f62b1f93`。
本文件是执行顺序与阶段验收的唯一当前计划；详细实现、试验和历史结论见
[迁移记录](Node_Host_Migration.md)、[启动说明](Node_Host_Startup.md)及下列证据。
本次压缩历史联调叙述，按交付依赖重新排序；不新增功能通过或硬件通过声明。

## 目标与范围

交付使用 Node.js 26／TypeScript、专用数学库及必要时 Rust 数学库的
Klipper 主机与完整原生 Moonraker 产品。在无 Python 环境完成构建、安装、
启动、打印、维护、升级、恢复和日常测试；以受控产品操作替代任意宏。
运动精度、停止保护与打印性能须经目标板和实机验证。现有 C MCU 固件与
C 运动内核可保留；语言与库选择服从数值正确性、调用成本和目标设备结果。
Rust 采用须有精度／性能证据，不作为未经验证的数值异常解法。

当前唯一机型范围为 **ANYRAID Cycnumbris 500 系列**；核验系列内硬件差异，
不推测配置一致。完整 Moonraker 是前期最高优先级功能主线，全部其他机型
适配放到最后。全面 Python 退役、完整功能替代及精度要求继续保留。

完整交付须同时满足：原有功能有替代及验收映射；固定上游 Moonraker 全量
契约闭合；宏场景完成受控操作替代；已知数值／崩溃问题关闭；目标设备
达标；默认及维护／测试入口无 Python；规定的集成与发布流程完成。
拒绝旧宏配置本身不代表宏产品化完成；功能替代与协议差异须分别记录。

## 审计结论与执行调整

已有独立编译包、原生运动与打印状态机、持久文件／身份／历史、受控操作
及模拟 MCU 验收设施。当前主要问题是这些资产尚未形成完整交付出口。
旧计划有 452 行，混入历史记录和多个“下一项”；本次改为单一执行队列。

新增的结构性发现：`runProductHost` 的代际关闭经 `product-service` 同时
关闭打印机和 Moonraker 服务。固定上游则在 Klippy 断开时保持 Moonraker
运行，发布断开事件、清理后端订阅并重连。当前 Mainsail 原生重初始化后
需要手动 TRY AGAIN；这不能证明标准重启兼容，也不能仅凭该现象判定
全部客户端恢复失败的根因。先处理服务生命周期，再补标准路由与页面验收。

## 唯一当前执行队列

### 1. 服务生命周期与标准重启（当前主要实现任务，解除 A 的恢复缺口）

当前增量已接入 `retirePrinter`：设备与请求单独退役，监听器、鉴权、数据库
及进程统计保留；停止失败不报告就绪。源码网络／模拟 MCU 回归和独立
编译包并发打印回归已通过，详见[退役边界证据](../host/contracts/native-generation-retirement-acceptance.json)。
这完成第一段退役边界；`runProductHost` 的 reinitialize 仍关闭整个服务。
**下一项是新代际重新绑定，并将数据库／身份／文件所有权与 adapter.release
分离，再接标准重启路由。** 当前文件／历史代际接口退役后暂不可用；不能
把保留监听器写成完整 Moonraker、标准按钮或实机恢复已通过。

保留现有进程与编译产品设施，明确进程级 Moonraker 所有者和可替换的
Klipper／MCU 代际。标准 Klippy 重启期间维持服务可查询、鉴权与持久资源
有效；设备未就绪时拒绝运动，状态和通知不得沿用旧 ready 快照。
不为此重新建设服务框架或默认拆分多个进程。

按以下依赖落实，先验证最小所有权边界，再接端点：

1. 允许服务观察设备断开、启动、就绪和失败，解绑旧运动端点／订阅／定时器，
   接入新代际；保留身份、文件及历史，避免请求碰到已释放资源。
2. 明确 `restart` 的主机重载与 `firmware_restart` 的 MCU 复位路径，核验
   停止确认、复位能力、传输所有权及配置重建。模拟复位必须实际清理同一
   MCU 模型的配置／shutdown 状态，不能以工厂新建模型冒充复位实现。
3. 接入对应 HTTP／RPC 的参数、响应、错误、权限和状态事件；复位策略不支持
   时明确拒绝，不返回假成功。已受理、设备重新就绪和失败必须可区分。
   旧受控 `/printer/host/reinitialize` 的语义与标准端点分别保留。
4. 验证未授权、重复／并发请求、打印中请求、停止失败、MCU 复位失败、启动
   失败及退出竞争。跨代请求不得执行于错误设备或重放打印；操作拒绝与上游
   差异记录到契约。故障仍需可查询，不能通过拒绝所有故障恢复关闭本任务。

通过条件：同一编译包的标准接口及生命周期契约有证据，固定实际客户端
通过相应按钮恢复就绪；模拟结果与物理 MCU 复位结果分开记录。

### 2. 固定客户端流程收口（完成 A）

复用现有 `client-probe` 与完整 MCU 时钟／热反馈设施。Fluidd 1.37.6、
Mainsail 2.19.0 分别验收页面上传、元数据、开始、暂停／恢复、完成、取消、
打印中刷新／断连、标准重启和失败后人工恢复。JWT 与显式可信网络场景
分别记录；Mainsail 可信回环初始化不等于用户登录通过。

页面上传使用真实客户端流程；文件选择器工具受阻时核对工具状态，改用
已有浏览器检查路径，API 测试只能作为独立接口证据。连续两轮没有新增
判别证据时登记阻碍并推进另一项合格任务，不无限重试。

完成后封存同一产物、依赖、配置、输入与报告；A 仍注明模拟设备边界和
完整 Moonraker 未闭合项。已有同产物运动状态 ABBA 查询对照不重复跑；
只有新变更、失败或新增未覆盖风险才扩大验证。

### 3. 装配与精度准入（准备并执行 B）

提前核实系列内硬件版本、printer.cfg／include、运动上限、MCU 固件、
真实停止输出、主机 OS／CPU、安装、访问及回滚资料；资料取得后列明配置
选项及宏场景对应的原生入口。缺失资料明确登记，不虚构适配器或空停止回调。

已知异常专项每次写明假设、能区分假设的输入／对照及判定条件，保留首个
失败证据。下一实验优先比较同一捕获用例在独立环境与不同实现中的表现；
不将大量成功随机重跑作为关闭依据，不放宽误差预算。精度原因或有证据的
隔离边界、目标板时序预算未成立前，不执行真实运动。

A、装配和精度准入通过后，在同一设备、输入和配置下比较旧 Python 与新
路径，包含空载和授权／上传／订阅／数据库负载；随后开展受控物理试验。
设备资料或独立环境暂不可得时，转第 4 项明确的 Moonraker 缺口。

### 4. 全量契约、受控操作和退役闭合（完成 C）

按固定上游逐组件展开参数、返回、错误、事件、权限、持久化、动态注册与
可选集成；每一批先映射现有实现和证据，再实现明确缺口。旧清单标签
不能代替当前审计，也不等待全仓台账整理完才实现已知缺口。

宏场景映射到类型化操作及迁移方式，验证前置条件、互斥、取消、持久化
幂等与故障恢复；不能只删除或拒绝配置来实现“替代”。Python 台账覆盖
运行、工具、构建／安装、日常测试和动态调用；冻结一次性参考后移除默认
解释器依赖。通用未替代功能仍须完成，机型实测单独在 G6 收口。

G1–G4 通过且退役条件成立后切换默认入口，经规定集成流程完成 G5。
其他品牌、系列、板卡组合及其物理验收统一留至 G6。

## 验证、推进与报告规则

同时仅推进一个主要实现缺口。任务须明确所属出口、用户路径、当前缺口、
依赖、改动、验证阈值及完成后的切换／退役动作；只读资料核查可交替进行，
这不是启用多个代理的授权。每轮更新本计划当前缺口与下一项，详细日志
进入契约证据，计划不再追加联调流水账。

验证分算法／模块、独立编译产品链路、目标设备三级。先跑受影响检查，
再跑一次相关同包流程；相同提交已覆盖且无新风险时不重复。服务生命周期
任务检查恢复耗时、资源回收和事件循环影响；高频路径检查吞吐与尾延迟。
每项替代均保留必要性能证据，桌面微基准不推导整机提速。

目标性能预算先依据设备和运动上限确定，再比较旧／新路径的 P95／P99、
步进发送提前量、队列饥饿、CPU／内存、长期稳定性与真实打印耗时。
数学回归使用固定参考、边界用例和明确误差预算。缺少目标板、旧路径对照
或预算时标记待验；成功样本不能覆盖未定因失败。

沿用当前任务工作树与分支，不重置既有历史；中文本地提交，当前不推送。
提交身份沿用已核实 GitHub 登录身份。后续按任务 PR → develop → master
集成，合并前核查实时远程状态。当前任务相对本地缓存 origin/develop 有
882 个未集成提交，应按依赖组织可审阅变更与检查，禁止一次性未验证合并；
此计数不代表已核实远程现状，也不是当前擅自推送／改写历史的授权。
正式部署须主线 PR 与规定门槛通过，依已有授权执行安装、验收及回滚。

报告只列：当前出口、新增通过的用户路径、移除的 Python 依赖、仍阻塞的
条件、下一项工作。暂不计算整体百分比；目标保持 active，不将计划审计
