## 总目标与完成定义

交付一个使用 Node.js 26／TypeScript、必要时使用 Rust 数学库的完整产品：
在无 Python 环境完成构建、安装、启动、打印、维护、升级与恢复；完整替代
约定上游的 Moonraker；以受控产品操作替代任意宏；运动精度和打印性能经
目标板及实机验证。现有 C MCU 固件与 C 运动内核可保留。库与语言选择服从
数值正确性、批量调用开销和目标设备结果，不以重写数量为目标。

完成须同时成立：默认入口和所有维护／测试入口不依赖 Python；原有功能
均有替代及验收映射；Moonraker 全量契约闭合；宏使用场景完成产品替代；
已知数值与崩溃问题关闭；目标设备达标；规定的集成和发布流程完成。
当前机型适配范围由用户于 2026-09-29 明确限定为 **ANYRAID 品牌
Cycnumbris 500 系列**。型号已确定，不再另选其他品牌或系列作为首台基线；
系列内具体硬件版本、配置和访问方式按实际资料核验，不推测其一致性。
**Moonraker 完整替代是前期最高优先级的功能主线；全部其他机型适配
放到最后。** 其他机型仍保留在总范围，不能阻塞当前系列交付，也不能
因暂缓适配而被标记为已完成。完整 Python 退役、精度与故障保护要求不变。

## 审计结论

### 9 月 30 日执行调整

最终目标保持不变，近期执行目标改为：**优先交付集成原生 Moonraker 的
Cycnumbris 500 产品包，以同一产物中的完整使用流程逐批验收，再闭合
全部 Moonraker 契约与 Python 退役；其他机型最后适配。**

此前顺序仍有一个风险：把“完整 Moonraker”作为开始产品装配的前置，
会使可选集成长期占据主线，真实安装、客户端和打印控制的连接问题发现
过晚。G1 是最高优先级的功能主线，不是禁止 G2 提前集成的串行关卡。
G3 也不是最后再测的阶段；已知数值故障始终阻止真实运动准入。

计划审计时 API Key 实现已提交；本地用户／JWT 当时只有未接入、未验证
的工作区草稿，后续进展见下文。177 个跟踪 Python 文件仍在，默认打印入口
仍为 Python，历史运动数值异常仍为 unresolved。本次仅审计与调整计划，
没有重跑历史测试，也没有新增硬件验收结论。

近期按以下交付批次推进；这些批次是 G1/G2 的执行切片，不替代 G0–G6：

| 批次 | 同一产品包中的可观察出口 | 验收边界 |
| --- | --- | --- |
| D1 身份与连接 | 配置服务完成用户创建、登录、HTTP/WS 授权、刷新、退出及重启持久化 | 先收口现有 JWT 草稿；验证失效令牌、跨用户隔离、错误与通知权限；记录未支持策略 |
| D2 文件与打印控制 | 登录后上传、读取元数据、启动、暂停、恢复、取消、查询历史，断线后重新同步状态 | 复用现有文件与打印控制实现，补连接缺口；独立编译产物先用模拟 MCU 验证，再用真实客户端验证兼容性 |
| D3 Cycnumbris 500 装配 | 该系列配置、真实停止输出、服务生命周期及受控操作接入同一产物，形成安装与回滚候选包 | 不等所有可选 Moonraker 集成；目标板运动须先通过相应 G3 门槛，模拟结果不算实机通过 |
| D4 完整性闭合 | 补齐其余固定上游契约、可选集成、配置与数据迁移，并关闭无 Python 交付缺口 | 逐项有证据；D1–D3 通过不能宣称完整 Moonraker 或最终交付 |

每批先核对现有入口和证据，仅实现缺失连接与行为，不重写已通过的底层
模块。批次出口必须含实际入口、产物、正常路径、故障恢复和必要性能证据。
每轮执行只推进一个主要缺口；尚未满足批次出口时明确写“进行中”，不能
以新增文件、单元测试数量或微基准代替交付进度。下一项固定为 D1 收口，
完成后进入 D2，除直接阻塞这两批的缺陷外不插入外围设备迁移。

性能验证分为变更级和交付级：每个替代运行相关正确性及性能检查；密码
哈希等低频重操作重点检查事件循环影响，高频鉴权与状态订阅检查吞吐和
尾延迟；D2 起在打印负载下同时施加上传、订阅与数据库活动，检查发送
提前量、队列饥饿、内存和打印耗时。使用相同输入、配置与设备比较旧路径
和新路径；缺少对照或目标设备时只报告开发回归结果，不宣称没有性能回退。
运动数学使用固定参考、边界用例和既定误差预算，不能放宽容差换通过。
已知崩溃与数值异常的关闭证据独立记录，不被这些批次的成功覆盖。

1. 9 月 26 日计划已有正确的大方向，执行缺少阶段出口与任务准入。
   在运动数值异常和实机入口尚未关闭时，连续扩展外围传感器，未优先
   消除整体交付阻碍。不能再用“又完成一个模块”推定接近完成。

## 实现与验证的任务准入

每项任务的最小记录：需求来源 → 用户路径 → 当前缺口 → 实现改动 →
验证依据／阈值 → 依赖 → 通过后的入口切换或退役动作。
没有对应阶段缺口的便利功能、绘图细节和额外防护不抢占主线。
当前保持一个主要实现任务；测试等待期间可做独立只读核查，不混入新改动。

验证分三级：算法／模块契约、发布产物完整链路、目标硬件验收。改动先跑
最小有意义的受影响检查；每个可交付组合跑完整链路，实机门槛必须在目标
环境完成。已有检查覆盖相同提交且无新风险时不重复。失败保留原始证据；
修复后的成功不能自动关闭未定因失败。

性能先给出预算再测量：规划／步进、时钟、发送队列及高频 API 重点看
吞吐、P95／P99、队列饥饿、命令提前量、CPU／内存、长时间稳定性及实际
打印耗时。阈值须对应目标板、运动上限和误差预算；当前桌面基准仅作
开发回归依据。传感器的微秒 CPU 开销不能推导整机打印提速。
完整 Moonraker 按固定上游展开方法、参数、错误、事件、权限、动态注册和
可选集成契约；可选组件不能因当前机器不用而被标为“完整替换完成”。
