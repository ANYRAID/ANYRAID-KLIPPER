# Klipper 与 Moonraker 集成交付计划

审计日期：2026-10-01；本批起点为已提交实现基线 `e2748d81`，初次审计基线为
`6c11ff43`；本批新增实现证据见当前队列。
本文件是执行顺序与阶段验收的唯一当前计划；详细实现、试验和历史结论见
[迁移记录](Node_Host_Migration.md)、[启动说明](Node_Host_Startup.md)及下列证据。
本次复核调整近期执行目标，区分已验证的集成接口与尚未贯通的产品入口；
硬件与完整交付门槛保持不变。

## 目标与范围

交付使用 Node.js 26／TypeScript、专用数学库及必要时 Rust 数学库的
Klipper 主机与完整原生 Moonraker 产品。在无 Python 环境完成构建、安装、
启动、打印、维护、升级、恢复和日常测试；以受控产品操作替代任意宏。
运动精度、停止保护与打印性能须经目标板和实机验证。现有 C MCU 固件与
C 运动内核可保留；语言与库选择服从数值正确性、调用成本和目标设备结果。
Rust 采用须有精度／性能证据，不作为未经验证的数值异常解法。

当前唯一机型范围为 **ANYRAID Cycnumbris 500 系列**；核验系列内硬件差异，
不推测配置一致。完整 Moonraker 是前期最高优先级功能主线，全部其他机型
适配放到最后。全面 Python 退役、完整功能替代及精度要求继续保留。

完整交付须同时满足：原有功能有替代及验收映射；固定上游 Moonraker 全量
契约闭合；宏场景完成受控操作替代；已知数值／崩溃问题关闭；目标设备
达标；默认及维护／测试入口无 Python；规定的集成与发布流程完成。
拒绝旧宏配置本身不代表宏产品化完成；功能替代与协议差异须分别记录。

## 审计结论与执行调整

已有独立编译包、原生运动与打印状态机、持久文件／身份／历史、受控操作
及模拟 MCU 验收设施。当前主要问题是这些资产尚未形成完整交付出口。
执行队列已统一，但仍需要把模块进度约束到可运行的产品交付批次。

初次审计的结构性发现：旧 `runProductHost` 的代际关闭经 `product-service` 同时
关闭打印机和 Moonraker 服务。固定上游则在 Klippy 断开时保持 Moonraker
运行，发布断开事件、清理后端订阅并重连。初次审计的 Mainsail 原生重初始化后
需要手动 TRY AGAIN；这不能证明标准重启兼容，也不能仅凭该现象判定
全部客户端恢复失败的根因。先处理服务生命周期，再补标准路由与页面验收。

初次审计基线进一步确认：`native-product-machine` 的一次性 `release` 同时
关闭上传、持久文件和 adapter；数据库由 adapter 提供，而服务器负责关闭。
因此仅新增 `ConfiguredMoonraker` 的重新绑定接口仍不足以使产品入口稳定
重启。所有权拆分必须连同 `runProductHost` 接入完成，不能只交付底层接口。
已有退役接口可复用；未完成的重新绑定草稿不计入已交付状态。

后续实现已将进程文件库、设备绑定与新 `createProcess` 资源工厂贯通
主机循环。此模式保留同一 Moonraker、数据库与身份；源码三代双模拟 MCU、
HTTP 失败回执及独立编译并发打印已验证。省略 createProcess 的旧适配器
保留一次性语义。后续 A1 已将文件元数据与权威日志移到进程所有者：旧设备
profile 释放后，查询、下载、授权上传、历史管理及事件仍可使用，新代际
复用同一资源。源码与独立编译包均已验收；标准重启整体验收和实际页面恢复仍未
完成，不能把 A1 计作整个恢复批次通过。

初次审计基线 `6c11ff43` 相对**本地缓存** `origin/develop` 有 884 个未集成提交，增加后续
审阅与集成成本。模块数量、提交数量和模拟用例数量均不作为整体完成率。
这两个已核实问题支持调整推进方式；本次未对过去全部耗时作因果归因。

### 本次确定的调整

本次目标复核结论：**保留完整目标，调整近期工作目标与交付粒度**。Node.js
26／TypeScript、完整 Moonraker、受控操作、精度／性能和全面 Python 退役
仍是最终验收要求。近期只实施 A 的已知恢复缺口，以实际产品行为决定
推进，不继续用模块扩展或重新审计代替交付。

本次复核确认：当前有 177 个跟踪 Python 文件，全部位于 klippy；默认
安装和 CI 仍依赖解释器；标准主机重启的软件增量见当前 A2，固件重启路由
尚未接入。断开窗口的进程文件／
日志归属现已贯通工厂、服务和路由，证据见当前队列的 A1 验收；不得据此
推定完整恢复和文件管理替代完成。
原始 Moonraker 注册目录仍含旧
状态标签，例如授权标签不能代表当前原生授权实现状态；按具体路径及
对应版本的证据判断，不把注册点计数或标签换算成完成率。

近期执行目标明确为：**同一编译产品进程保持 Moonraker 可用，重建 Klipper
设备后由实际 Fluidd／Mainsail 的标准重启流程恢复就绪，并保留身份、文件与
历史**。完成该用户路径后封存 A；新增模块只能作为这条路径的必要依赖。
完整语言迁移和完整 Moonraker 继续作为最终目标，不以 A 代替最终验收。

将当前恢复批次拆为下列可审阅增量，顺序固定。每项先接通产品入口，完成
受影响的正确性、清理和必要性能检查，再进入下一项；实际客户端检查在
相关接口完成后尽早执行，最终仍须对同一个编译包完整验收。

| 增量 | 最小交付行为 | 完成后推进 |
| --- | --- | --- |
| A1 断开窗口持久资源 | 旧设备实际释放后，原身份仍能查询文件、元数据、下载和历史；授权上传不触发打印；设备动作不可用；新代接入后无旧请求串代或资源泄漏 | RESTART |
| A2 主机重启 | 标准 HTTP／RPC RESTART 接通主机重载；故障后的显式恢复、重复请求和退出竞争有确定结果；原服务保留，客户端能观察断开与重新就绪 | FIRMWARE_RESTART |
| A3 固件重启 | 独立 MCU 复位策略清理原设备状态并重建配置；停止或复位失败保持可查询且不 ready；能力不支持时明确拒绝 | 固定客户端完整流程 |
| A4 候选包封存 | 同一编译包通过 Fluidd／Mainsail 页面上传、作业控制、标准重启、断连和进程恢复；记录哈希、契约差异、尾延迟、发送提前量和资源回收 | 封存 A，进入 B 准入 |

A1–A4 分别对应下文 L1／L2 的余项、L3 的两条路径及 L4，不是新增并行
队列。A 可以明确注明未闭合的外围契约；这些未完成项仍阻塞 C 的完整
Moonraker 声明。B 只使用已验收契约，G3 准入仍须通过；不得因此提前切换
默认入口或放宽真实运动条件。

加速规则：每次实现先给出一个可观察的失败场景和完成判据，禁止在达到
判据前引入无关组件、新框架或库选型。连续两轮没有新增判别证据时，记录
具体阻碍并选取同一出口内不受阻的任务，不进行无目的重跑。只有新事实
改变依赖或验收条件时再调整计划；批次完成立即形成可审阅增量及集成材料。
运动诊断与机型资料只做必要的前置核查，不抢占当前服务实现，也不拖延到
实机试验当天才处理。后续记录以本计划、可复用启动说明和版本化证据为
入口，不继续向历史迁移记录追加逐轮操作流水。

| L2 代际切换 | `configured-server`、请求／订阅／文件与维护门禁 | 等待旧请求与停止确认后接入新设备；旧授权、订阅、采样和上传引用不得访问错误代际；停止或启动失败仍可查询且不 ready |
| L3 标准重启 | `product-host-control`、标准 HTTP／RPC、MCU 复位策略 | RESTART 与 FIRMWARE_RESTART 按各自语义执行；不以同一个重初始化或新模拟模型代替；重复、故障恢复及退出竞争有明确结果 |
| L4 同包验收 | 现有独立编译产品验收及固定 Fluidd／Mainsail | 同一进程内登录身份、连接、文件及历史保留，标准按钮恢复可用并重新订阅；重启不重放打印，失败不伪报成功 |

资源所有权先在实际产品入口形成，代际接口与其共同验收。数据库维护须
在每次请求时绑定当前代际门禁，并在整个操作期间保持同一门禁；仅更换
打印控制器而沿用已关闭门禁不合格。文件／历史查询已属于保留服务，不能
在后续重启实现中重新依附设备代际。

首代服务出口现已接通：有界机器清单解析后创建进程资源、授权监听器和
持久恢复日志，随后才预检设备并取得 adapter。初次配置、adapter 与 MCU
配置失败均保持查询与连接；确认清理后可显式 RESTART，清理失败拒绝
新代际。listening 与设备 ready 独立，不创建替身控制器；进程文件读路由
只注册一次。源码与同包恢复／并发打印证据见
[首代失败恢复验收](../host/contracts/native-process-bootstrap-acceptance.json)。

普通重启的最后一项软件判据已通过：主／辅 MCU 分别注入实际配置 CRC
变化和持续 shutdown，同一编译产品的 HTTP／RPC 连续重启保持失败可查询，
不发送 reset、不改写现有配置、不发送虚假就绪通知；原连接、身份、文件和
历史仍可用。恢复原配置后可复用 MCU；持续 shutdown 仍失败。
有界故障分类不依赖异常文本，清理未确认优先拒绝恢复。源码、编译产品及
同产物并发打印／资源性能证据见
[普通重启固件故障验收](../host/contracts/native-standard-restart-fault-acceptance.json)。
这封存 A2 的软件判据，实际按钮和完整恢复批次仍须 A4。

reset，再接入新设备配置。主／辅 MCU 的原模型须实际清除配置和 shutdown；

## 验证、推进与报告规则

同时仅推进一个主要实现缺口。任务须明确所属出口、用户路径、当前缺口、
依赖、改动、验证阈值及完成后的切换／退役动作；只读资料核查可交替进行，
这不是启用多个代理的授权。仅在交付批次通过、失败改变路径或出现新阻碍
时更新本计划；日常进度在工作报告中说明，详细日志进入契约证据，计划
不再追加联调流水账。未完成代码草稿不作为可交付增量，保持可验证基线。

每个实现批次按“明确失败的用户路径 → 贯通产品入口 → 必要回归与性能 →
同产物客户端验收”推进。把持久资源、设备连接、路由与清理当作一次交接
处理；只有模块通过时继续本批次，不跳往另一模块。运行验证期间冻结其
源码，等待原执行句柄真正结束后再修改；保留首个失败及修复后的验证，避免
混用不同版本的证据。不存在新增变更或判别目的时不重复已通过的测试。

验证分算法／模块、独立编译产品链路、目标设备三级。先跑受影响检查，
再跑一次相关同包流程；相同提交已覆盖且无新风险时不重复。服务生命周期
任务检查恢复耗时、资源回收和事件循环影响；高频路径检查吞吐与尾延迟。

订阅、上传与打印并发。既有测试阈值属于桌面回归门槛，不能直接作为

链路。历史证据及源码哈希保留原版本，新批次生成新证据，避免改写历史。
