# Node.js 26 主机迁移

## 目标与当前状态

目标是以 Node.js 26 / TypeScript 全面替换仓库内 Python（包括主机、
构建、烧录、诊断和文档工具），集成完整 Moonraker 功能，并将宏转换为
消费级产品的受控操作。数学库按精度和目标板性能选择；必要时采用 Rust。
保留 MCU C 固件及现有 C 运动内核不构成 Python 残留。

初始基线：`ce7002be`，218 个 Git 跟踪的 Python 文件：`klippy` 179、
`scripts` 32、`lib` 6、`docs` 1。当前生产入口仍是 Python；`host/`
是迁移中的实现，尚不可用于控制打印机。不得将新增 TS 文件等同于原模块已替换。

开发从最新 `develop` 建立独立任务工作树，任务 PR → `develop` → `master`。
本机检查通过后还需集成与目标硬件验证；生产部署须在授权范围内执行。

## 宏的产品设计方向

面向用户提供打印准备、开始、暂停、恢复、取消、换料、校准等具名操作，
使用有版本的类型化参数与设备能力约束；用户不必编写模板或 G-code。
每个操作具有显式状态机、前置条件、进度、取消边界、超时、幂等标识、
资源互斥和可恢复记录。参数验证完成后才允许产生设备副作用。

温度上限、归零/位置有效性、运动范围、挤出温度等保护必须由主机核心执行，
不能依赖宏正确编写。断连/断电后的运动恢复须重新验证位置和设备状态，
不能盲目重放命令。旧宏导入必须生成可检查的操作或给出不支持原因；不得
通过 JS eval 或无限制脚本保留原有风险。兼容与专家入口需明确能力边界。
完整契约尚未全部实现。当前 `host/src/operations/print.ts` 提供版本化开始请求、
温度和文件标识校验、幂等开始、暂停/恢复状态约束、取消及失败停机。
取消会立即请求设备停止，并等待活动操作结束和安全停机确认后才报告取消完成。
设备适配器必须兑现 AbortSignal，拒绝取消后的迟到副作用，并在控制边界
重新验证安全条件。当前只有模拟适配器测试，没有连接打印机。
持久化幂等记录、重启恢复、文件注册、设备能力检查、操作/停机超时、
完成事件及下一任务生命周期仍未接入，不能作为生产级宏替代品交付。

## 精度与性能门禁

- 使用 binary64；MCU 的 64 位计数通过 BigInt/原生整数传输，禁止隐式降精度。
- 以原算法、独立解析解、几何/方程残差三种证据验证数学模块。
  奇异、近奇异、边界、不可达、NaN/Infinity、超大/超小量级须单独测试。
- 普通模块记录耗时与内存；热路径记录吞吐、p50/p95/p99、分配、GC、
  事件循环延迟和原生调用开销。校准与频谱计算必须离开运动调度线程。
- 同一机器、输入、预热、重复次数比较原 Python 与候选版本；本机微基准
  不代表目标板吞吐或打印速度。最终须在支持的目标板跑真实 G-code 回放、
  步进时间戳差分、满负载 API/文件传输及长时间运行，验证无队列饥饿。
- 未建立目标机型号、固件配置、允许步进时间误差、最大打印负载的实测基线
  前，禁止宣称运动精度和打印速度完整通过。
- 所有替代完成后移除 Python 入口、运行/构建依赖和临时 Python 对照执行器；
  保存版本固定的对照数据。逐文件审计及无 Python 环境构建/运行均须通过。

## 当前开发命令

安装 Node.js 26 后：

```sh
cd host
npm install
npm run typecheck
npm test
npm run bench
```

`bench/math.ts` 暂时调用仓库原 Python 模块作为开发对照，不属于新主机运行时。
它以固定种子生成 1,000 组几何与线性系统，5 次预热、21 次测量，
输出硬件、运行时、误差、残差、中位数及 p95；中位数慢于 Python 则失败。
当前范围仅覆盖三球定位和 4×4 双 RHS 线性求解。其余函数与病态输入的
差分、坐标下降 Worker 隔离以及目标板测试仍须补齐。

### 首轮开发基准（2026-09-19）

Linux x64、AMD Ryzen 5 3500X、Node 26.9.0、Python 3.12.13：

| 1,000 次计算 | TS 中位数 / p95 | Python 中位数 / p95 |
| --- | --- | --- |
| 三球定位 | 0.889 / 0.940 ms | 2.782 / 2.816 ms |
| 4×4 双 RHS 求解 | 2.813 / 4.827 ms | 8.794 / 8.871 ms |

最大位置误差 `1.457e-13`、相对 Python 的最大位置差 `1.421e-14`、
最大方程残差 `3.331e-16`。这是固定输入域的单次本机运行记录，不能
推广到病态矩阵、所有硬件或整机打印性能。5 个单元用例和严格类型检查通过。

### 频谱校准与操作层（2026-09-19）

`host/src/calibration/` 用锁定版本的 `fft.js` 实现 NumPy Welch PSD 的
Kaiser(beta=6)窗、去均值、50% 重叠、单边谱、三轴求和及频率归一化。
保留上游 `N / T` 采样频率约定。每个 isolate 的 FFT 计划缓存有界，
原始采样为 binary64，退化时间戳和非有限输入被拒绝。
`SpectrumExecutor` 单任务运行，转移采样缓冲区所有权，支持取消、超时和
失败清理；终止 Worker 后才释放任务槽。它不是完整 shaper 搜索器。

开发对照需要可导入 NumPy 的 Python，仍仅用于开发，不属于主机运行依赖：

```sh
cd host
PYTHON=/path/to/oracle/python npm run bench:spectrum
```

与原 `ShaperCalibrate.calc_freq_response` 对照，同一桌面 CPU、NumPy 2.5.3，
3 次预热、15 次测量的最近一次结果：

| 三轴采样数 | TS 中位数 | NumPy 中位数 | Worker 完整墙钟时间 |
| --- | --- | --- | --- |
| 8,192 | 1.017 ms | 1.150 ms | 54.463 ms |
| 65,536 | 5.487 ms | 5.071 ms | 59.590 ms |
| 262,144 | 21.708 ms | 23.521 ms | 83.861 ms |

最大谱绝对差 `6.37e-12`，按 `1e-12` 下限缩放的最大相对差约 `1.06e-11`。
Worker 测量的主线程心跳 p99 为 1.26–1.68 ms（1 ms 采样分辨率），
这不是实时调度上界。Worker 启动成本单独报告，未与 Python 多进程启动比较。
中等数据量 TS 中位耗时约慢 8%，尚不能宣称整个校准性能门禁通过；
继续评估目标板、完整校准和并发负载后决定是否需要 Rust。首次实现曾慢约
3 倍，已通过消除逐样本回调和缓存 FFT 计划优化，未放宽精度阈值。

当前 13 项测试与严格类型检查通过；远程 CI、硬件和原 Python 项目全量检查
尚未运行。数学微基准与频谱基准不能代替运动/打印吞吐验收。
